## Persiapan staging

1. Connector khusus `tamukita-staging` berjalan dari image `cloudflare/cloudflared:2026.10.1` dan hanya bergabung ke external network `tamukita-staging-xwcuty_staging-origin`; `TUNNEL_TOKEN` tersimpan hanya di environment rahasia layanan Dokploy. Jangan commit token ke repository atau memasukkannya ke environment tingkat project. Lihat [panduan Tunnel resmi Dokploy](https://docs.dokploy.com/docs/core/guides/cloudflare-tunnels) dan [rilis resmi cloudflared](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.1).
2. Rute `staging.tamukita.io` pada Tunnel `tamukita-staging` mengarah ke web staging port `3000` lewat network origin khusus; CNAME proxied mengarah ke tunnel tersebut dan pemeriksaan HTTPS lulus. Pemeriksaan konfigurasi sebelumnya menunjukkan route itu memang tidak terpasang pada `tigakaki1`. Tunnel tidak berbagi network dengan service Dokploy lain.
3. Environment aplikasi sudah menyimpan `NEXT_PUBLIC_APP_URL`, `POSTGRES_PASSWORD`, dan `AUTH_SECRET` khusus staging pada service Compose Dokploy. Jangan menyalin atau membagikan nilai rahasia.
4. Audit environment awal 19 Oktober 2026 dilakukan sebelum kredensial R2 media ditambahkan. Saat ini web dan worker mempunyai enam variabel R2; bucket privat/publik berbeda, URL media HTTPS, CORS staging aktif, dan signed object read/write langsung berhasil pada marker privat. Ini belum membuktikan endpoint upload aplikasi, proses gambar worker, atau baca publik melalui domain. `XENDIT_SECRET_KEY` yang ada bukan key development; jangan gunakan untuk transaksi staging. Nilai Resend/email belum diverifikasi sebagai non-production. Simpan nilai integrasi hanya pada environment Compose Dokploy, lalu deploy ulang jika perubahan source memerlukannya. ## Persiapan production

1. Buat Cloudflare Tunnel khusus production yang terpisah dari `tamukita-staging`, tetapi jangan pasang public hostname atau ubah DNS dulu.
2. Di Compose service aplikasi production, set `TAMUKITA_ORIGIN_NETWORK=tamukita-production-origin` dan `NEXT_PUBLIC_APP_URL=https://tamukita.io`. Buat Compose service connector di environment `production` dari `docker-compose.production-tunnel.yml`, gunakan nama network yang sama, dan simpan token Tunnel hanya sebagai secret service Dokploy. Deploy aplikasi dahulu agar membuat network origin, lalu deploy connector. Connector hanya bergabung ke network origin; jangan gunakan token atau network staging.
3. Buat rahasia production secara terpisah melalui secret store Dokploy. Jangan gunakan nilai staging atau contoh di `.env.example`.
4. Siapkan bucket R2 media/backup, Resend, backup offsite, dan webhook alert production. Uji Xendit Test Mode dan email non-production di staging; keputusan operasional/legal harus disetujui sebelum memakai kredensial live atau membuka layanan ke publik.
5. Sebelum cutover, periksa migrasi, health container, backup terjadwal, restore di VPS, serta alert aplikasi/host. Service production belum perlu memiliki domain di tab Domains Dokploy karena jalur publik memakai Cloudflare Tunnel.
6. Setelah semua gate dan go-live disetujui, buat public hostname `tamukita.io` menuju `http://web:3000` pada Tunnel production. Ini mengganti record apex yang sekarang menuju halaman parkir; biarkan record MX/email dan record domain lain tetap utuh. `www` belum termasuk hostname yang dipilih.
7. Pastikan `/api/health` publik sehat, lalu set GitHub Actions repository variable `PRODUCTION_HEALTH_URL=https://tamukita.io/api/health` dan jalankan production smoke check. Nyalakan auto-deploy hanya setelah prosedur rilis dan rollback production ditetapkan.

Tempatkan konfigurasi pada lingkup yang benar; jangan kirim nilai secret ke repository atau chat:

| Lingkup | Nilai/secret | Catatan |
|---|---|---|
| Compose aplikasi production | `POSTGRES_PASSWORD`, `AUTH_SECRET`, `NEXT_PUBLIC_APP_URL=https://tamukita.io`, `TAMUKITA_ORIGIN_NETWORK=tamukita-production-origin` | Password database dan auth harus baru, unik, dan hanya untuk production. |
| Compose Tunnel production | `TUNNEL_TOKEN` | Token milik Tunnel khusus production; simpan sebagai secret service Dokploy. |
| Fitur aplikasi | `XENDIT_SECRET_KEY`, `XENDIT_WEBHOOK_TOKEN`, `XENDIT_REFUND_WEBHOOK_TOKEN`, `RESEND_API_KEY`, `EMAIL_FROM`, serta kredensial R2 media | Buat bucket serta sender terpisah. Mulai dari Test Mode dan email non-production di staging. Jangan aktifkan kredensial live sebelum pilot/go-live disetujui. |
| Backup VPS | `R2_BACKUP_ACCESS_KEY_ID`, `R2_BACKUP_SECRET_ACCESS_KEY`, `BACKUP_BUCKET`, `BACKUP_COMPOSE_PROJECT_NAME`, `BACKUP_AGE_RECIPIENT`, dan berkas `BACKUP_AGE_IDENTITY_FILE` | Simpan backup key dan age identity di host/secret store backup; batasi key ke bucket backup dan verifikasi restore sebelum pilot. |

Skrip backup memakai endpoint Cloudflare R2 dari `R2_ACCOUNT_ID` secara default. Biarkan `BACKUP_S3_ENDPOINT` kosong dan `BACKUP_S3_ALLOW_HTTP=false` pada VPS. Override endpoint tersedia untuk integration drill S3-compatible; HTTP hanya diizinkan untuk host lokal yang dibatasi oleh skrip dan harus memakai flag eksplisit.

Sesudah container production pertama berjalan, temukan nama Compose project yang dipakai Dokploy dengan `docker ps --filter 'label=com.docker.compose.service=postgres' --format '{{.Names}} {{.Label "com.docker.compose.project"}}'`. Isi nama itu ke `BACKUP_COMPOSE_PROJECT_NAME` pada `/etc/tamukita/backup.env`; helper backup/restore mencari satu container PostgreSQL berdasarkan label project tersebut dan service `postgres`, tanpa bergantung pada nama direktori Compose di host.
